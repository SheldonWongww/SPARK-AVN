9 个完整 TTA 的 `result.json` 字节完全相同：Tent01/02、FSTTA01/02、EAM01/02/03、FeedTTA01/02。共同结果相对 Source 是 **SR +0.21751 点、SPL −0.01383 点**，不能表述为两个指标均改善。

从 `console.log` 的 `actions [...]` 按 `scene_episode` 提取每条 episode 的生成动作块，得到：

- FSTTA01/02、EAM01/02/03、FeedTTA01/02 与 Tent01 的 1839 条动作序列完全相同。Tent02 仅一条动作序列不同，但该条所有结果字段仍相同。
- FSTTA03 仅四条动作序列不同，三条 episode 的结果不同；Tent03 有 867 条动作序列不同。
- FeedTTA03 与 ATENA01/02/03 都未跑完，已完成部分的动作序列和结果逐条等于 Tent01 的对应前缀。日志末尾在 episode 中途，没有 traceback，不能据此判定方法崩溃或收敛。
- Tent01、FeedTTA01/02 与 Source 有 1061/1839 条动作序列不同；FeedTTA01/02 同时报告最终参数漂移为 0。共同的 SR 差值缺乏“有效适应带来收益”的证据。

这里核对的是日志中的生成动作块，归档不含 simulator pose 轨迹。当前 v4 实现会从复制的 FP32 readout 重新计算动作并强制首个动作 token；无更新路径也可能与原生 Source 解码不同，因此新实现应以原生分数校准零更新路径。

`updates` 是优化器调用次数，不能视为参数真实变化次数。最终 `relative_param_drift` 也不替代逐步参数变化检查。`overridden_first_actions=0` 比较的是内部 readout 与 adapter 动作，不是原生 decoder 动作；不能据此断言轨迹没有被改变。

方法诊断中的具体线索：

- **FSTTA**：01 共 459 个 slow window，只执行一次 slow update、跳过 458 次；02 执行 320/459；03 执行 114/114。旧低 LR 不足以形成可靠的 fast/slow 比较。
- **EAM**：01/02/03 分别执行 10037/40146/40146 次更新，辅助使用率约 84.51%/72.49%/72.65%；03 最终漂移 0.00271665，但动作序列仍与 Tent01 完全相同。不能只看 loss、update 次数或漂移判定部署决策已改变。
- **FeedTTA**：01/02 各消费 1839 条二值反馈、各更新 1839 次，但最终漂移为 0。其 `alpha=+0.1` 在当前公式下是 gradient scaling；03 的 `alpha=-0.2` 才发生随机梯度反转。搜索同时改变 LR、gamma 与 alpha，无法单独归因。
- **ATENA**：01/02/03 分别查询 273/284、198/312、293/294 条反馈，即 96.13%/63.46%/99.66%。阈值 0.1、0.15 几乎等于全反馈；这些都是前缀统计，不能外推完整流。

按“完整 val_unseen SPL 优先、SR 次之、低 LR 打破平局”选择 **Tent01：Adam、LR=3e-8、last_ln、update_interval=1**。它与 Tent02 指标持平，Tent03 SPL 较低；Tent01 并未超过 Source SPL。val_seen 若要与归档 val_unseen 配成同一个结果，必须保留 v4 的执行路径；若改为原生分数加适应增量的路径，需明确是新实现，不能暗中沿用旧 val_unseen 指标。

可复用绑定位于 `summary.json.reuse_bindings`：Source 1839 条的结果摘要、ZIP digest、服务器原路径和本地 raw 路径；Tent01 的原配置及配置 digest、结果 digest、选择规则。这些绑定用于复用和审计，不补齐缺失的历史 provenance。
